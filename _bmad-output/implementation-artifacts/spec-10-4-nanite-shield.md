## Intent

**Problem:** Nanite Shield is registered (Story 10.1) with five empty `stats: {}` maps, so the PRD §13.4 defense pick is a card that changes nothing. Two things are missing: nothing consumes the `shieldCharges` field `PLAYER_STATS_BASE` already reserves for this story, and `PlayerDeathSystem._applyDeath()` — the single seam every life cost funnels through — has no notion of a hit being absorbed instead of paid for.

**Approach:** Author Nanite Shield's five per-level `stats` maps (PRD §13.4) over three fold fields — `shieldCharges` (max charges, already in the base), `shieldRechargeMs` (per-charge regeneration interval), `shieldKnockback` (the Lv5 break pulse flag). A new `NaniteShieldSystem` owns the RUNTIME charge count + recharge timer (the fold owns only the derived MAXIMA) and exposes `tryAbsorb()`; `PlayerDeathSystem._applyDeath()` consults it first and returns early on an absorb. Content + one seam read at the existing death choke point; no new pool, no new entity.

## Boundaries & Constraints

**Always:**
- The absorb intercepts at `_applyDeath()` — the SHARED body — so it covers BOTH the ship↔enemy contact path AND the `pendingDeath` programmatic path (a Black Hole detonation, Story 6.2; a Mirror Reflector weight-kill, Story 6.3). Those producers exist specifically to route "the SAME death flow as a contact death, subject to the SAME invuln/game-over guards" (`PlayerState.js`), and the level-up i-frame gate already protects both uniformly. The shield is another guard on that one flow, not a second one beside it.
- An absorb costs a CHARGE and nothing else. `lives` is unchanged, `gameOver` is never set, the ship is NOT teleported to arena center, the run multiplier is NOT reset (`resetMultiplier` is never reached), and `deathSeq` is NOT bumped — so the grid death ripple, the death screen-shake, and the death SFX cue all stay silent. Keeping the streak and the position is the whole value of the pick.
- An absorb grants `SHIELD_ABSORB_INVULN_MS` of the EXISTING `playerState.invulnMs` window. This is forced, not decorative: without it, an enemy in contact drains every charge on consecutive ticks (3 charges in 50ms) and the item does nothing. Assign it DIRECTLY, not via `Math.max` — `_applyDeath` is only ever reached with `invulnMs === 0` (its caller returns early while any window is in flight), so there is never a larger window to shrink, and this matches `_applyDeath`'s own `ps.invulnMs = PLAYER_INVULN_MS` respawn assignment. That same guard is why a charge can never be spent while the player was already safe.
- At most ONE absorb per fixed step, on both paths — the contact loop already `break`s after `_applyDeath()` returns and the forced path already `return`s, so this falls out of the existing structure and must not be loosened.
- Per-level `stats` are TOTALS at that level, never deltas, per the `PlayerStats.js` AUTHORING CONVENTION — even where the `desc` text reads as a delta. L2 (`'Recharge 15s'`) must ALSO restate L1's 1 charge; L3 (`'2 charges'`) must restate the 15s; L4 must restate the 2 charges; L5 must restate the 10s. `desc` strings stay exactly as registered; do not rewrite them to match the totals.
- The fold owns the MAXIMA only (`shieldCharges` is the CAP, not the live count). The live count and the recharge timer are RUNTIME state on the system, because `recomputePlayerStats` resets and re-derives the whole store on every card pick — a live count kept there would be silently restored to full by picking any unrelated item.
- When the fold RAISES the max (first acquisition, or a charge-count rung), the live count gains the SAME delta immediately, then clamps to `[0, max]`. Picking "2 charges" gives you the second charge now; it does not make you wait a recharge for the card you just picked. A max that DROPS (an Epic 12 remnant) clamps the live count down.
- Zero per-frame allocation. The recharge tick is scalar arithmetic; the Lv5 pulse iterates the pools through a hoisted `forEachActive` collector (it mutates only `x`/`y`, never the active set, so no materialization pass is needed).
- The Lv5 pulse fires ONLY when the FINAL charge breaks (live count reaches 0) AND knockback is enabled. A Lv5 break from 3→2 or 2→1 fires nothing.
- The pulse is a POSITION displacement, not a velocity impulse. `EnemySystem`/`ArmoredSystem` recompute velocity toward the ship every tick, so a velocity force vanishes on the next tick — the identical reasoning `BlackHoleSystem` records for its gravity nudge. It runs from `PlayerDeathSystem`'s slot, after every mover has integrated, so the displacement persists.
- The pulse skips telegraphing (`telegraphMs > 0`) enemies — a spawning-in enemy is inert to world forces, exactly as `BlackHoleSystem` gravity treats it — and clamps every pushed enemy back inside the arena interior, inset by its own radius (the `ARENA_BORDER_INSET` convention `spawnPlacement`/`PinwheelSystem` already use), so a break against a wall cannot shove enemies outside the drawn border.
- The pulse's reach is the five COMBAT archetype pools (`enemyPools`), never `deathPools` — the Black Hole and the Mirror Reflector are immune to AoE, the same scoping `BombSystem.detonateAt` already applies.
- All three sanitizers are SAFETY guards, never balance levers, in the shape `FIRE_INTERVAL_FLOOR_MS` / `SPREAD_MAX_WAYS` established: a junk store must not be able to grant unbounded charges, recharge once per tick, or hang a loop.
- With no Nanite Shield owned, every shipped behavior is byte-for-byte identical to today: the same life cost, the same respawn, the same multiplier reset, the same `deathSeq` bump, the same card draw for a given rng stream.

**Block If:**
- The shipped `desc` strings would have to change for the numbers to agree — that is a PRD contradiction, not an authoring choice.

**Never:**
- Do not author `stats` for Afterburner (Story 10.5), and do not re-tune Overcharge's or Spread Cannon's numbers.
- Do not add a HUD readout, an on-ship shield ring, a break particle burst, screen shake, or an absorb SFX cue. The story's ACs are the gameplay integration; the feedback surface is Epic 4's and is deliberately deferred (see Design Notes).
- Do not add a new `PlayerState` field, a new pool, or a new entity type. Do not change what `deathSeq`, `killedEnemies`, or the invuln gate mean.
- Do not let the pulse DAMAGE, kill, release, or score enemies — it only moves them.
- Do not make the shield absorb while the player is already invulnerable or already game-over. Those guards live in `fixedUpdate`, ABOVE the `_applyDeath` call sites, and must stay there — do not relocate, duplicate, or reorder them into the shield check.
- Do not implement Phase Armor / Slipstream or any fusion behavior (Epic 12).

## Design Notes

**Why the absorb intercepts `_applyDeath()` and therefore covers `pendingDeath` too.** Two readings of "a shielded hit consumes a charge instead of costing a life" are available: contact hits only, or every life cost. The codebase selects the second. `PlayerState.js` documents `pendingDeath` as existing so its two producers get "the SAME death flow as a contact death, subject to the SAME invuln/game-over guards" — i.e. the guards are deliberately uniform across both paths, and the level-up i-frame gate already saves the player from a Black Hole detonation exactly as it saves them from a seeker. A shield that lapsed on the detonation path would be the first guard in this system to discriminate between them, and would contradict the story's own purpose ("a single mistake isn't always fatal"). Intercepting inside the shared body is also the smaller change: one early return, no new branch at either call site.

**Why the live count is NOT in `playerStats`.** `recomputePlayerStats` resets every field to base and re-derives the whole store on EVERY card pick. A live charge count kept there would be silently refilled by picking any unrelated item — a free shield reset once per level. So the fold owns the derived MAXIMA (`shieldCharges` is a cap) and the system owns the live count. This is the first Epic-10 item whose effect has runtime state rather than a pure stat read, and the split is the reason `PLAYER_STATS_BASE`'s reserved `shieldCharges` field is a maximum rather than the obvious "current charges".

**Why an absorb must grant i-frames.** The lethal test runs every fixed step against a still-overlapping enemy. With no window, a 3-charge shield is fully drained in 3 ticks (50ms) and the player dies anyway — the item would be strictly worse than it reads. The window is what converts a charge into a survivable moment, and reusing `invulnMs` means no new state and no new gate.

```js
// itemRegistry.js — L4 entry: TOTALS, though the desc names only the recharge
{ level: 4, desc: 'Recharge 10s',
  stats: Object.freeze({ shieldCharges: 2, shieldRechargeMs: 10000 }) }

// PlayerDeathSystem._applyDeath — the whole integration, at the top of the shared body
if (this.shieldSystem && this.shieldSystem.tryAbsorb()) {
  ps.invulnMs = SHIELD_ABSORB_INVULN_MS;  // no life, no respawn, no deathSeq, no multiplier reset
  return;
}

// NaniteShieldSystem._pulse — outward position nudge, linear falloff (BlackHoleSystem._pull inverted)
const d = Math.hypot(e.x - ship.x, e.y - ship.y);
if (d > 0 && d < SHIELD_KNOCKBACK_RADIUS) {
  const push = SHIELD_KNOCKBACK_PUSH * (1 - d / SHIELD_KNOCKBACK_RADIUS);
  const inv = push / d;
  e.x = clampInterior(e.x + (e.x - ship.x) * inv, e.radius, ARENA_WIDTH);
  e.y = clampInterior(e.y + (e.y - ship.y) * inv, e.radius, ARENA_HEIGHT);
}
```

**Position, not velocity.** `EnemySystem` and `ArmoredSystem` rewrite `vx`/`vy` toward the ship every tick, so a velocity impulse is erased before it moves anything — the exact trap `BlackHoleSystem` records for its own gravity. The pulse therefore displaces `x`/`y` directly, and runs from `PlayerDeathSystem`'s late slot so no mover overwrites it this tick.

**No feedback surface, deliberately.** An absorb bumps no `deathSeq`, so it emits no grid ripple, no screen shake and no SFX — and this story adds none. That is scope, not oversight: the two ACs are the gameplay integration, and a shield HUD/ring/burst belongs with Epic 4's juice vocabulary. The consequence is that a Lv1 absorb is currently invisible apart from the enemy failing to kill you; `absorbSeq` is published now so that feedback work has an edge to consume without touching this system again.
