## Intent

**Problem:** Spread Cannon is registered (Story 10.1) with five empty `stats: {}` maps and no offer guarantee, so the PRD's "base-weapon evolution, always offered by Lv3" is a card that changes nothing and may never be seen. Two things are missing: `FiringSystem` spawns exactly ONE bullet per volley along the aim vector with no notion of a multi-bullet volley, and `drawCardOffer` is a pure weighted draw with no way for an item to guarantee itself a slot.

**Approach:** Author Spread Cannon's five per-level `stats` maps (PRD §13.3) as two new fold fields — `spreadWays` (bullets per volley) and `spreadArcDeg` (the volley's TOTAL cone, centered on aim) — plus the `fireRateMult`/`damageMult` rungs that reuse Story 10.2's already-shipped seams. `FiringSystem` fans each volley across the cone by rotating the live aim vector by a cached per-bullet offset. Separately, item definitions gain a declarative `guaranteeFromLevel` field, and `drawCardOffer` reserves a slot for an unowned, otherwise-eligible guaranteed item once the run level reaches it. Both are content + one seam read; no new system.

## Boundaries & Constraints

**Always:**
- The `°` figure is the volley's TOTAL cone angle, centered on the aim direction — NOT the gap between adjacent bullets. The intent's own use of degrees for a volley pattern fixes this: PRD §13.5 describes Sunburst as a "full 360° ring", where 360 can only mean total angular coverage. Bullets are spaced EVENLY across that cone: for `N` ways and arc `A`, bullet `i` is offset `-A/2 + i·A/(N-1)` from the aim direction (`N === 1` → offset 0). All shipped counts are odd, so a center bullet always travels exactly along aim.
- Per-level `stats` are TOTALS at that level, never deltas, per the `PlayerStats.js` AUTHORING CONVENTION — even where the `desc` text reads as a delta. So L3 (`'+30% fire rate'`) must ALSO restate the L2 spread, and L5 must restate the L4 arc and the L3 fire rate. `desc` strings stay exactly as registered; do not rewrite them to match the totals.
- `spreadWays` and `spreadArcDeg` are additive/count fields (base 0, per the fold's naming convention). `spreadWays: 0` — no spread item owned — means the single-bullet volley. `FiringSystem` treats any sanitized ways `< 2` as the single shot.
- With no Spread Cannon owned, every shipped behavior is byte-for-byte identical to today: same one bullet per volley, same spawn position, same velocity, same cadence, same stamped damage. The single-shot path must stay the literal pre-10.3 code, not a one-iteration special case of the fan loop.
- The fire-rate and damage rungs flow through the EXISTING Story 10.2 seams (`fireRateMult` → effective interval, `damageMult` → stamped `bullet.damage`) and stack ADDITIVELY with Overcharge, exactly as the fold specifies. No second damage or cadence path.
- Every bullet in a volley is stamped with `damage` at acquire — the `Bullet.js` obligation Story 10.2 wrote specifically for this story. A recycled bullet carries the previous shot's damage and the collision-side fallback cannot detect it.
- The offer guarantee is EXCLUSION-SUBORDINATE. It reserves a slot only for an item whose normal `cardWeight` is already `> 0`; banished, maxed, remnant and unowned-in-a-full-track all still exclude it. Story 8.5 banish permanence and Story 10.1 exclusion purity outrank the guarantee — a banished Spread Cannon is never offered again, guarantee or not.
- The guarantee holds from the threshold level onward while the item stays UNOWNED (level 0), not only on the crossing level-up. It costs no `rng()` draw, so an inactive guarantee leaves the existing draw stream bit-identical.
- Zero per-frame allocation in `fixedUpdate`. The per-bullet offset table is recomputed only when `(ways, arcDeg)` changes — i.e. on a card pick — and reuses its buffers.
- Both new sanitizers are SAFETY guards, never balance levers, in the shape `FIRE_INTERVAL_FLOOR_MS`/`PLAYER_BULLET_MIN_DAMAGE` established: a junk `spreadWays` must not be able to spawn an unbounded number of bullets in one fixed step.

**Block If:**
- The shipped `desc` strings would have to change for the numbers to agree — that is a PRD contradiction, not an authoring choice.

**Never:**
- Do not author `stats` for Nanite Shield or Afterburner (Stories 10.4/10.5), and do not re-tune Overcharge's numbers.
- Do not add piercing, bouncing, or a per-bullet cap/spawn-position rework — Spread Cannon fires the SAME bullets through the SAME pool and the SAME `CollisionSystem`.
- Do not change what a `°` means for Sunburst, or implement any fusion behavior (Epic 12).
- Do not make the guarantee override banish/maxed/remnant/slot-full exclusion, and do not reintroduce the retired zero-weight "fill to CARD_OFFER_SIZE" safety net.
- Do not let one trigger-pull emit N fire SFX cues.

## Design Notes

**Why total-cone and not per-bullet step.** Read as a per-bullet gap, the shipped ladder gives arcs of 24° → 64° → 132° → 176°: a Lv5 volley would fire nearly perpendicular to aim, which is not a "spread" for a twin-stick. Read as the total cone it gives 12° → 16° → 22° → 22°, a volley that grows DENSER (more bullets, near-constant width) — which matches the story's purpose, "my default firing scales into the mid-game", i.e. more DPS down the aim line. PRD §13.5's "full 360° ring" is the same author using degrees for a volley's total coverage, and settles it.

**The saturation shape is deliberate content, not a bug.** L3 adds only fire rate and L5 adds only damage on top of an unchanged 22° cone; the `stats` maps still restate the carried-forward values because levels are totals. A reviewer reading `desc` alone will see "L3 promises only +30% fire rate" and may read the restated spread as a copy-paste error — it is not.

```js
// itemRegistry.js — L5 entry: TOTALS, though the desc reads as a delta
{ level: 5, desc: '9-way spread / +35% damage',
  stats: Object.freeze({ spreadWays: 9, spreadArcDeg: 22,
                         fireRateMult: 0.30, damageMult: 0.35 }) }
// FiringSystem — per volley (ways > 1); offsets cached, rebuilt only on a level change
const step = arcRad / (ways - 1), start = -arcRad / 2;      // even spacing, aim-centered
const c = cosOff[i], s = sinOff[i];                          // cached per offset
const dx = input.aimX * c - input.aimY * s;                  // aim is already unit
const dy = input.aimX * s + input.aimY * c;
b.x = ship.x + dx * ship.radius; b.vx = dx * BULLET_SPEED; b.damage = damage;
```

**Two counters, not one.** `shotsFiredCount` stays honest to its name (bullets spawned) because the whole point of the story is that this number now moves; the AUDIO cue is a per-trigger-pull event, so it moves to `volleysFiredCount`. Left as-is, a 9-way build would peg the `AUDIO_SFX_FIRE_MAX_PER_FRAME = 2` cap on every tick.

**Converging bullets.** `CollisionSystem` pass 1 skips an enemy already hit this tick, so several spread bullets landing on one enemy in one tick deal one bullet's damage and the others fly on unconsumed. Pre-existing behavior, deliberately untouched here — a spread build's advantage is coverage, not stacked single-target burst.
