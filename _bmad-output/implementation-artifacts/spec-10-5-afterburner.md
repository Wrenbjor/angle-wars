## Intent

**Problem:** Afterburner is the last Epic-10 item still carrying empty `stats: {}` — the registry, the fold, the card offer and the slot limits all know about it, but picking it does nothing. It is also the only one of the four whose effect is not a pure stat read: levels 2–5 add a *dash* — a discrete, cooldown-gated burst with i-frames (Lv3+), contact damage (Lv4+) and a burning trail (Lv5) — so it needs a new button on every shipped input method and a new sim system, not just a numbers table.

**Approach:** Author the five `stats` maps as TOTALS over five fold fields (`moveSpeedMult`, `dashCooldownMs`, `dashIFrames`, `dashDamage`, `dashTrail`), feed `moveSpeedMult` into BOTH `PlayerMovementSystem`'s thrust acceleration AND its max-speed cap — scaling the cap alone delivers nothing above ~1.15 because the thrust/drag equilibrium, not the cap, becomes the binding constraint (see Design Notes) — and add one `DashSystem` that owns the dash's runtime state (cooldown, active window, direction) exactly as `NaniteShieldSystem` owns the shield's live charges. The dash button mirrors the smart bomb end-to-end (keyboard `Q`, gamepad triggers, an on-screen touch button). Dash contact damage routes through a damage helper **extracted** from `CollisionSystem`'s pass 2, so an armored enemy behaves identically whether a bullet or a dash hits it, and a dash kill scores, drops XP, sprays particles and ripples the grid exactly like a bullet kill.

## Boundaries & Constraints

**Always:**
- The five `stats` maps are TOTALS at that level, `Object.freeze`d, and every `id`/`name`/`title`/`track`/`rarity`/`maxLevel`/`desc`/`guaranteeFromLevel`/`fusion` on the entry is untouched. `desc` strings are never rewritten to match the totals.
- Every new fold field is read through a **sanitizing reader** in the shape of `FiringSystem._mult` / `NaniteShieldSystem._maxCharges` (missing store → base, non-finite → base, clamp to a named safety constant). The store is the only channel — no system reconstruction on a pick.
- `dashCooldownMs` fails **CLOSED**: a missing store, a non-finite value or a value `<= 0` means *no dash at all* (the pre-10.5 movement path exactly), not a dash at the floor. A finite positive value below `DASH_COOLDOWN_FLOOR_MS` clamps UP to the floor. Level 1 owns no dash.
- `moveSpeedMult` scales the thrust acceleration AND the speed cap, by the SAME factor, and leaves `SHIP_DRAG_RETAIN_PER_SEC` untouched. The measurable requirement is the ACHIEVED top speed, not the cap value: at every shipped rung the ship must actually reach `SHIP_MAX_SPEED × mult` under sustained held input. Scaling the cap alone satisfies no rung above Lv1 and is the defect this story was re-specced to fix.
- `PlayerMovementSystem` stays the SOLE writer of `ship.vx`/`vy`/`x`/`y`. `DashSystem` owns dash *state* and the damage sweep; movement reads that state and applies the velocity. Two movers is the failure mode this rule exists to prevent.
- Every consumer of "the dash is happening right now" — the i-frame gate, the damage sweep and the trail — reads ONE published flag, `DashSystem.movementActive`, captured at the top of `DashSystem.fixedUpdate` BEFORE any mutation. That is exactly the value `PlayerMovementSystem` read earlier in the same tick, so the protected window, the damaged window, the trailing window and the moving window are the SAME set of ticks. Reading the mutable `active` from a system that runs after `DashSystem` offsets the window by one fixed step and leaves the tail of the dash unprotected.
- A Lv4+ dash damages each enemy at most ONCE per dash, not once per tick. Without that, a dash into a wall with an enemy pinned between ship and wall lands one hit per tick of the window from a single press.
- Any death or respawn CANCELS an in-flight dash. A respawn re-parks the ship at arena centre; an un-cancelled dash window then flings it back out during its invulnerability.
- The gamepad dash binding must be a DIGITAL button in the standard mapping. Phaser's `Button.threshold` defaults to `1` (`node_modules/phaser/src/input/gamepad/Button.js:75`), so an analog trigger (6/7) never fires `down` and never reports `pressed` until fully pulled — the bomb's bumpers are digital, which is why this class of bug could not surface before.
- The on-screen touch dash button is drawn, hit-tested and counted as activity ONLY while the dash is actually owned. An always-present button costs every touch player a disc of aim-stick area for an action most runs never unlock.
- `DashSystem` is registered immediately AFTER `CollisionSystem` and BEFORE `ScoringSystem`, so its kills append to the live per-tick kill latches (`killedEnemies`, `bulletKillCount`, `bulletKillX/Y/Xp`, `bulletDamageCount`) rather than into arrays `CollisionSystem` has already reset. Both neighbours are load-bearing and must be pinned by index assertions.
- Dash contact damage goes through the SAME armor-respecting path bullets use (a helper extracted from `CollisionSystem` pass 2, called by both), never a bespoke copy and never the bomb's `hp`-ignoring outright release.
- The dash sweeps only `enemyPools` — the five COMBAT archetype pools, never `deathPools`, never the Black Hole or Mirror Reflector pools.
- Zero per-tick allocation on every dash path, idle and active: hoisted collectors, reused scratch, length-reset arrays.
- The dash button is bound on ALL THREE shipped input methods (keyboard, gamepad, touch) at full parity with the smart bomb, including the pause freeze and the level-up-modal drain. A binding that exists on only some methods leaves the item unusable on a shipped platform.
- The keyboard binding must not collide with a browser or game-flow input: not `Ctrl` (Ctrl+W closes the tab on the web build), not `Enter`/`Space`/pointer (the game-over restart inputs), not `Shift`/`M`/`-`/`+`/`Esc`/`P`/`S` (already bound).

**Block If:**
- Wiring the dash into any input method would require changing how `resolveActiveMethod` picks the active method, rather than adding one more signal to `isGamepadActive` / `isKbmActive` / `touch.isActive()`.
- Extracting the damage helper from `CollisionSystem` cannot be done without changing observable bullet-vs-armor behavior for any existing test.

**Never:**
- No fusion consumption (Epic 12 owns Slipstream), no new pooled-entity system, no rebinding/config UI, no HUD cooldown readout, no reduced-motion branch for the dash trail.
- The burning dash trail is **cosmetic only** — it deals no damage and leaves no lingering zone. A damaging ground trail would be a new pooled-entity system, which Epic 10 explicitly defers to Epic 11 (Mine Layer), and this story's own acceptance criteria enumerate the dash's mechanical effects as i-frames (Lv3+) and contact damage (Lv4+) only.
- The dash never scales with `damageMult` — Overcharge applies to the player's *fire*, and the dash is not fire.
- Do not rename `bulletKill*` / `bulletDamageCount` across their six consumer systems; widen the documented contract in place instead.
- Do not put the live cooldown or the active window in `playerStats` — the fold resets and re-derives on every pick, so a live timer there would be refunded by picking any unrelated item.

## Design Notes

**Why `DashSystem` sits after `CollisionSystem` instead of next to the movement it drives.** The dash needs two things at once: its state current before `PlayerMovementSystem` (slot 2), and its kills appended to `CollisionSystem`'s per-tick latches, which that system RESETS at the top of its own `fixedUpdate` (slot 11). Only one of those is achievable from a single registration slot. The kill latches win, because they are the difference between a Lv4 dash that pays out score, XP, particles and audio and one whose kills are silent — the `BombSystem` failure mode, which is deliberate there (a panic button should not farm score) and would be a bug here (XP is progression currency; a dash that eats enemies without granting XP is a hidden penalty for using the item). The cost is that movement applies the dash window one fixed step (16.7ms) after it opens. That is imperceptible, deterministic, and pinned by the ordering test; the alternative is a hole in the reward loop.

**Why `moveSpeedMult` scales `SHIP_ACCEL` as well as the cap (Resolution DW, 2026-07-23).** The cap is not the ship's real speed limit — the thrust/drag equilibrium is, whenever it sits lower. With `k = SHIP_DRAG_RETAIN_PER_SEC^dt = 0.015^(1/60) = 0.93240`, the fixed point of `v ← (v + SHIP_ACCEL·dt)·k` is `SHIP_ACCEL·dt·k/(1−k) = 597.7 px/s`. The base cap of 520 sits below that, so today the cap binds. Raise the cap alone and it stops binding at `mult ≈ 1.149`: Lv2 (624), Lv3/Lv4 (650) and Lv5 (702) all top out at a flat 597.7, so four of the item's five rungs are indistinguishable in play while their cards read +20/+25/+25/+35%. That is exactly what the first attempt shipped, and the whole suite passed because every assertion pinned the fold value or the cap expression — never the speed the ship reaches.

Scaling accel by the same factor moves the equilibrium to `597.7 × mult`, which is above `520 × mult` for every positive multiplier, so the cap binds at every rung and the achieved speed is exactly `520 × mult`. Two properties fall out for free: at `mult === 1` both products are their bare constants, so the no-item path stays byte-identical (the AC that rules out the alternative fix of lowering global drag); and because the velocity profile scales in SPEED rather than in TIME, time-to-top-speed and stopping distance-in-time are unchanged at every rung — the ship gets faster, not floatier. The third candidate, scaling integrated displacement, was rejected for shrinking the effective arena. The guard against this class of regression is a test that measures `hypot(vx, vy)` after driving to steady state; a test that pins `cap === SHIP_MAX_SPEED * mult` is green against the broken implementation and must not be treated as coverage.

**Why one published `movementActive` instead of reading `active`.** `DashSystem` sits after `CollisionSystem` (see above) and therefore after `PlayerMovementSystem`, so movement always reads the dash flag as the previous tick left it while `PlayerDeathSystem` and `ParticleSystem` — both later than `DashSystem` — read it as this tick left it. Those are different windows: measured on the first attempt, movement ran the dash on ticks 2–12 while `iFramesActive()` was true on ticks 1–11, leaving the final ~22px of travel unprotected and contradicting this story's own i-frame AC. Capturing `movementActive = active` as the very first statement of `fixedUpdate` republishes precisely what movement acted on, so one field makes the moving, protected, damaging and trailing windows the same ticks by construction rather than by each consumer compensating for the offset.

**Why one hit per dash rather than per tick.** The sweep re-runs each tick at the ship's current position, which is right for covering the dash path — but the arena clamp can hold the ship stationary for the whole window, so an enemy pinned between ship and wall took ~10 hits and pushed ~10 damage-units into the Story 9.2 DPS governor from a single press. A per-dash stamp (`e._dashHitSeq === dashSeq`) is the conventional melee-sweep semantic, costs no allocation, and cannot go stale across pool reuse because `dashSeq` only ever increases.

**Why the fold carries flags and an interval, not the dash's magnitudes.** `DASH_SPEED`, `DASH_DURATION_MS` and `DASH_CONTACT_DAMAGE` are constants, not `stats` fields, for the same reason `SHIELD_KNOCKBACK_PUSH` is: the fold is ADDITIVE, so any magnitude placed there would double if a second item ever authored the same key. Only `dashCooldownMs` has to live in the fold (it is the one value the levels actually change), and it inherits the same hazard `shieldRechargeMs` documents — a second dash item would make the dash slower, not faster. `dashIFrames`/`dashDamage`/`dashTrail` are flags in the `shieldKnockback` shape.

**Why `_cooldownMs()` fails CLOSED while the shield's recharge reader fails OPEN.** A junk `shieldRechargeMs` still leaves a shield that works, just at a floored rate — the item's capability does not hinge on the value. A junk `dashCooldownMs` is different: the interval IS the enable flag (Lv1 has no dash precisely because the field is 0), so falling back to a floor would MINT a dash the build never bought. Disabled is the honest fallback; the floor applies only to a value that is already positive.

```js
// itemRegistry.js — L4: TOTALS, though the desc names only the cooldown + damage
{ level: 4, desc: '2s dash cooldown + dash damages on contact',
  stats: Object.freeze({ moveSpeedMult: 0.25, dashCooldownMs: 2000,
                         dashIFrames: 1, dashDamage: 1 }) }

// PlayerMovementSystem.fixedUpdate — the dash branch replaces thrust/drag/cap
if (this.dashSystem && this.dashSystem.active) {
  ship.vx = this.dashSystem.dirX * DASH_SPEED;   // constant-velocity burst
  ship.vy = this.dashSystem.dirY * DASH_SPEED;   // drag + thrust deliberately skipped
} else {
  const mult = this._moveSpeedMult();            // read ONCE, applied at BOTH ends
  const accel = SHIP_ACCEL * mult;               // step 1 — else the cap never binds
  const cap = SHIP_MAX_SPEED * mult;             // step 3
  /* step 2 (drag `k`) deliberately untouched — feel scales in speed, not in time */
}
// steps 4 (integrate + arena clamp) and 5 (facing) run for BOTH branches

// DashSystem.fixedUpdate — FIRST statement, before any mutation. This is exactly
// what PlayerMovementSystem read earlier this tick; every later consumer reads it,
// so the moving / protected / damaging / trailing windows are the same ticks.
this.movementActive = this.active;

// PlayerDeathSystem.fixedUpdate — the gate, after the invuln countdown block
if (this.dashSystem && this.dashSystem.iFramesActive()) return;  // no life, no charge
// ...and inside _applyDeath(), so a respawn is never flung out by a live window:
this.dashSystem?.cancel();
```

**Why the trail is cosmetic.** "Burning" is the only word in the intent suggesting otherwise, and everything else points the other way: this story's acceptance criteria enumerate the dash's mechanical effects as i-frames (Lv3+) and contact damage (Lv4+) and stop there; Epic 10's stated scope is stat-stackers on existing seams "with no new entity systems required"; and a lingering damage zone is exactly the pooled-entity system Epic 11's Mine Layer owns. A damaging trail would also silently change the Lv5 rung from a visual payoff into the epic's strongest offensive item, on a defense-track pick.
